# SnapShare scaling plan

## Assumptions and estimates

- There are 10 million registered users, and 10% (1 million) are active each day.
- Each daily active user uploads one photo and requests 50 feed pages per day.
- A photo is 2 MB and its generated thumbnail is 50 KB (0.05 MB).
- For the estimates, a day has 86,400 seconds and a year has 365 days; MB and TB are decimal units.
- These are average rates, not peak rates. Actual traffic will be burstier, so the system should be load-tested and provisioned with headroom.
- Storage estimates count one copy of each original and thumbnail, with no compression, replication, or deletion; database and other operational data are excluded.

| Quantity | Calculation | Estimate |
|---|---:|---:|
| Photo uploads | 1,000,000 per day / 86,400 seconds | about **11.6 uploads/second** |
| Feed page views | 1,000,000 users × 50 pages / 86,400 seconds | about **579 feed views/second** |
| Original photo storage per year | 1,000,000 × 2 MB × 365 | **730 TB/year** |
| Thumbnail storage per year | 1,000,000 × 0.05 MB × 365 | **18.25 TB/year** |
| Total photo-file storage per year | 730 TB + 18.25 TB | **748.25 TB/year** (about **0.75 PB**) |

SnapShare is **read-heavy**: the estimate is about 50 feed-page reads for every photo upload, before counting the many image requests generated by each feed page.

### What each component solves

- **CDN:** Serves frequently requested thumbnails near users and reduces image latency and load on the application and object-storage origin.
- **Load balancer:** Distributes incoming API traffic across healthy app servers and provides a single entry point for scaling them horizontally.
- **App servers:** Handle authentication, photo-upload requests, feed assembly, and coordination between storage, the database, cache, and queue.
- **Cache:** Keeps hot feed data and metadata in memory so repeated reads avoid hitting the database for every feed request.
- **Database primary:** Reliably stores authoritative user, follow, and photo metadata and accepts metadata writes.
- **Database read replica:** Serves scalable feed and metadata reads without sending all read traffic to the write primary.
- **Object storage:** Stores large original photo and thumbnail files durably and separately from the relational metadata database.
- **Thumbnail queue:** Buffers thumbnail-generation jobs so upload traffic does not have to wait for image processing to finish.
- **Thumbnail worker:** Consumes queued jobs, creates a 50 KB thumbnail from each original, and saves it to object storage.

## Photo upload flow

1. The user sends an authenticated photo upload request to SnapShare; the load balancer routes it to a healthy app server.
2. The app server validates the request and writes the original photo to object storage under a unique key.
3. The app server records the photo's owner, storage key, and processing status in the database primary.
4. The app server enqueues a thumbnail-generation job containing the photo ID and original storage key, then returns an upload confirmation without waiting for thumbnail processing.
5. A thumbnail worker takes the job, reads the original from object storage, and generates the 50 KB thumbnail.
6. The worker writes the thumbnail to object storage and updates the photo metadata to mark it ready; the CDN can then cache and serve it when requested.
7. Feed requests read photo metadata through the cache and read replica; image URLs point to the CDN, which serves cached thumbnails or fetches them from object storage on a cache miss.

## Trade-offs

- **Asynchronous thumbnails improve upload responsiveness, but add eventual consistency:** the upload can succeed before the thumbnail is ready, so clients need a processing state or a temporary original/placeholder display.
- **A read replica increases read capacity, but can lag behind the primary:** a newly uploaded photo may not immediately appear in a feed read from the replica; routing a user's immediate follow-up reads to the primary improves freshness but adds primary load.
- **Caching and CDN delivery reduce latency and origin traffic, but make freshness and invalidation harder:** use versioned or unique image URLs and expire cached feed data so updates do not remain stale indefinitely.
- **Object storage scales cheaply for large files, but introduces a separate dependency:** database metadata and photo objects must be coordinated, and failed uploads or processing jobs need retry and cleanup handling.
